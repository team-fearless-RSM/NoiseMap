THE PROJECT

About NoiseMap

Making local sound observations easier to understand and act on.

Our approach

NoiseMap is a Team Fearless NRL Changemakers project. The goal is to record observations at selected locations, present patterns over time and help the team document awareness and follow-up actions.

How a staffroom alert is intended to happen

  1. Sound activity is detected. The LM393 module provides a threshold-based sensor signal. It does not identify the source of a sound.
  2. Device firmware evaluates warnings. The device-side logic must decide when a warning is unsuccessful and maintain the warning count. The current Cloud Function does not listen to audio or independently count classroom warnings.
  3. The device submits an alert event. For an alert, the authenticated upload must include event: "staffroom_alert", warning_count: 3 and a valid episode ID.
  4. The server validates and records it. The Cloud Function checks the device credential, registered device, assigned location and payload. It saves the raw ADC observation and creates one alert record for that episode.
  5. Authorised staff review it. Team members can acknowledge or resolve the alert and separately enter actions that have actually been taken.
What is and is not automated today

The backend can process a valid authenticated alert event sent by device firmware. End-to-end automatic warning counting and physical sensor alert delivery still require firmware implementation and live hardware testing. The manual TEST ALERT form creates only an alert record; it does not come from the sensor and does not create an Action Tracker record. The current backend does not automatically create Action Tracker recommendations or send SMS/WhatsApp notifications.

Measurement integrity matters.

The current LM393-based prototype detects sound activity and provides raw sensor readings. These readings represent combined sound from the surroundings; they do not identify individual sources and are not calibrated sound-pressure measurements. NoiseMap will only display dB or dB(A) if suitable calibrated measurement hardware and a documented calibration method are implemented.

ROADMAP · FUTURE EXPANSION

Beyond Schools

NoiseMap is being developed around school environments first. With suitable hardware, calibration, permissions and field testing, the same location-based monitoring approach could be explored in other settings.

Monitor changing sound activity around construction zones, compare readings across work areas and record follow-up actions when configured limits are exceeded.

Possible application

What would need to change?

Measurement hardware: Use suitable sound-level measurement equipment and a documented calibration process before reporting dB or dB(A).

Site-specific thresholds: Configure limits according to the applicable location, operating context and authorised guidance—not one universal threshold.

Reliable connectivity: Provide secure device registration, verified heartbeats, stable data transmission and clear offline reporting.

Responsible response: Give authorised local teams access to alerts and an auditable action tracker, with privacy and data-retention safeguards.

Important

These are potential future applications, not currently deployed NoiseMap services. The present LM393 prototype records raw ADC sound-activity readings; it does not provide calibrated dB(A), identify a specific sound source or establish a legal violation.

Further research

AI-based sound classification could be explored later using appropriately collected and labelled samples. Any predicted category would be an estimate, not proof of the exact source, and would require privacy safeguards and real-world testing.
